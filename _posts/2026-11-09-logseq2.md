I'm working on several papers at once. For this blog post, let's call them `[[Death Star Security]]`, `[[Droid Rights]]`, `[[Holocron Access Controls]]`, and `[[Imperial Surveillance]]`.

I use Logseq's daily journal to keep track of my TODOs. This works well until I want to know how a *paper* is going. The tasks are spread across journal pages, and even if I find all of them, that doesn't tell me whether the paper is being drafted, waiting on coauthors, or ready to submit.

I wanted one page with each paper's stage, venue, deadline, and open tasks. My first idea was to give each paper its own tag and add that tag to every TODO. But that meant typing `#Death Star Security` five times if I had five tasks for that paper. Forget the tag on one task and it silently disappears from my list. That is not setting one's self up for sucess.

So this is a blog post on how I solved the issue by using page properties for the paper's status and nested tasks for the TODOs.

A quick note: I'm still on Logseq OG. The database version looks cool, but I haven't switched yet, so that's what these queries are written for.

## Make a template for the papers

First, check that the names you want to use aren't already topic pages in your graph. If you have an `[[Droid Rights]]` page for general notes, for example, its existing references could get mixed into your paper tasks.

On a page called `Templates`, add this block:

```
- Paper page
  template:: paper
  template-including-parent:: false
	- tags:: paper, active
	  stage:: drafting
	  venue:: 
	  deadline:: 
	  coauthors:: 
	- #+BEGIN_QUERY
	  {:title "Open tasks"
	   :query [:find (pull ?b [*])
	           :in $ ?current
	           :where
	           [?p :block/name ?current]
	           [?b :block/path-refs ?p]
	           [?b :block/marker ?m]
	           [(contains? #{"TODO" "DOING" "NOW" "LATER" "WAITING"} ?m)]]
	   :inputs [:current-page]}
	  #+END_QUERY
```

Now open `[[Death Star Security]]`, click into the first block, type `/template`, and select `paper`. Fill in the properties. Repeat for the other three pages.

**The properties need to be in the first block on the page.** Otherwise Logseq treats them as block properties and the dashboard won't find them. That's also why the template has `template-including-parent:: false`: it leaves out the `Paper page` wrapper when you insert it.

I'm using two tags, `paper` and `active`, so I can remove a finished paper from the dashboard by deleting `active` without losing the page. The other properties are just columns I want to see. For `stage`, I stick to `idea`, `drafting`, `revising`, `submitted`, `r&r`, and `accepted`. Logseq won't stop me from using `revise` on one paper and `revising` on another, you must be consistent for this to work. 

The query at the bottom shows open tasks for that paper. It filters out `DONE` and `CANCELED` tasks, which is more useful to me than scrolling through everything in Linked References.

## Keep writing tasks in the journal

In my daily journal I write a paper reference once, then indent the tasks under it:

```
- [[Death Star Security]]
	- TODO review exhaust port security
	- WAITING hear back from the engineering team on if the thermal exhaust port's 2-meter-wide shaft is an issue
```

Logseq's `:block/path-refs` includes references from parent blocks. Both tasks are therefore associated with `[[Death Star Security]]`, even though neither has its own tag. They show up in the query on that paper's page.

If I already have a revision checklist, I can also put the TODOs directly on the paper page. Those show up too.

## The dashboard

Create a page called `Papers` and add these two blocks:

```
- {{query (and (page-tags paper) (page-tags active))}}
- #+BEGIN_QUERY
  {:title "Open tasks, active papers"
   :query [:find (pull ?b [*])
           :where
           [?b :block/marker ?m]
           [(contains? #{"TODO" "DOING" "NOW" "LATER" "WAITING"} ?m)]
           [?b :block/path-refs ?p]
           [?p :block/tags ?t1] [?t1 :block/name "paper"]
           [?p :block/tags ?t2] [?t2 :block/name "active"]]}
  #+END_QUERY
```

The first query finds pages tagged `paper` *and* `active`. Switch the results to table view if they appear as a list, then show the `stage`, `venue`, and `deadline` columns. That's my at-a-glance paper tracker.

The second query collects open tasks from all those papers. It's basically the same query as the one on each paper page, except it looks for pages with both tags instead of the current page.

I added `Papers` to my favorites so I can get to it from the sidebar.

## Check that it works

Before trusting the dashboard, add a test task to today's journal:

```
- [[Death Star Security]]
	- TODO test task: determine if this is a fully operational battle station
```

It should appear in the open-task query on `[[Death Star Security]]` and in the dashboard. If it appears on the paper page but not the dashboard, check whether `tags:: paper, active` ended up in the page's first block and then delete the test task afterward.

## A few limitations

The dashboard's tasks are grouped by the journal day they were written on, rather than by paper. The breadcrumb tells me which paper each belongs to, and I can use the query on an individual paper page when I want that view.

Your indentation matters -- e.g., If I accidentally move a TODO out from under the paper reference, it loses that association. 

Finally, the properties don't update themselves. If I submit `Droid Rights` but leave its stage as `drafting`, the dashboard will continue to say `drafting`. I just check the page once a week and update whatever has changed. I could probably build something more elaborate, but then I'd have another thing to maintain.
